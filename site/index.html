Built before: Agents.ai

A Manifest V3 extension that operates on any third-party website: a React side panel, a service worker gateway, and content scripts that find and act on elements in pages they have never seen. The FastAPI backend plans actions over the Chrome DevTools Protocol and reads only what changed in the page, which cut page payloads by 70 to 95%.

The video shows it working on live sites. The board shows how the backend, worker and content scripts fit together.

What carries over to your extension

  • Finding the right field on sites I don't control: labels, aria references, names, shadow DOM, pages that re-render.
  • Writing into React and Angular forms so the value sticks, which a plain .value = does not.
  • The MV3 service worker lifecycle: Chrome stops idle workers, so nothing important can live there by accident.
  • On-demand injection and the hand-off between popup, worker and page.

What this extension does the opposite of

  • Agents.ai kept sessions and recordings in Chrome storage. Here the storage permission is absent, so the API does not exist at runtime.
  • Agents.ai used debugger and tabs. Here: activeTab and scripting, nothing else.
  • Agents.ai logged steps and screenshots for the agent. Here nothing is logged, and the report carries no values.
  • Agents.ai clicked and navigated on its own. Here nothing is clicked or submitted; the professional does that.

Try the real extension in Chrome

  1. Download the extension build and unzip it.
  2. Open chrome://extensions, turn on Developer mode, choose Load unpacked, pick the folder.
  3. Open the demo web app and choose a portal. It sends the extension a 2-minute ticket and opens the portal.
  4. On the portal tab, click the SafeFill icon, then Fill this page.

What to look for

Open the payer portal from the web app, then switch to a different tab and press Fill: it refuses, because the ticket is bound to the portal's site. Wait two minutes and press Fill: the request has expired. Inspect the service worker: chrome.storage is undefined.

How a value finds its field, or doesn't

Plausibility is deliberately broad and acceptance is deliberately narrow. A wide net means a near-miss shows up as a second candidate and turns into a skip, instead of a guess.

Four layers keep data from staying or leaving

"Stores nothing, logs nothing" is not one promise in the code. It is four separate barriers, and each has its own test.

Manifestwhat Chrome allows
No storage permission, so chrome.storage is undefined. No static content scripts, no web-accessible resources, one host permission.
Browser test reads typeof chrome.storage in the live worker: undefined.
Content Security Policywhere data can go
connect-src is locked to your backend. Even a bug cannot send a value anywhere else.
Browser test: a fetch to another origin is blocked before any request leaves.
Policy gate in CIwhat the code may contain
Fails the build on storage APIs, logging, beacons, sockets, form submission, synthetic clicks or keys, dynamic code, extra network calls, extra permissions.
10 tests inject each violation and expect a failure.
Report shapewhat leaves the page
The engine's report has no value fields. The worker rebuilds it from an allowlist of fields and drops anything else. Errors travel as codes, never messages.
Tests assert that no record value appears in any report or in the popup.

One fill, from click to review

The web app never hands values to the extension. It hands over a short-lived ticket; the extension trades it with your backend only after the professional presses Fill on the matching site.

One honest limit: JavaScript cannot wipe a string from memory. What the design guarantees is that values are only held inside one function call, never in a variable that outlives the fill, and the worker itself is discarded by Chrome when idle.

What the Web Store changes, and how the check handles it

The store adds content-verification data (a _metadata/ folder) to every package and may add store-managed keys such as update_url to the manifest. The verifier lists exactly those exceptions, prints each one it applies, and fails on anything else. I'd confirm the list on the first staging upload, which is also why that upload is scheduled early.

The detail that usually gets missed

When a job uses a GitHub environment, the default OIDC subject becomes repo:ORG/REPO:environment:release and drops the branch or tag. A trust policy written against tags would then never match, and one written loosely would accept any workflow that reaches that environment. So I customize the subject to include the workflow file, and the cloud side checks it.

GitHub: subject claim template

PUT /repos/ORG/REPO/actions/oidc/customization/sub
{

Rules every workflow follows

  • No pull_request_target anywhere: it runs fork code with the base repo's permissions.
  • Third-party actions pinned to full commit SHAs, not tags that can move.
  • Checkout with persist-credentials: false; default permissions: contents: read.
  • Test tooling installed with npm ci --ignore-scripts; the build itself has zero dependencies.
  • The list of allowed release signers comes from a protected environment only admins can edit, never from the tagged code.

One decision for you

A Web Store service account can manage every item under the publisher account; it cannot be limited to one item. If the staging item lives under the same publisher, the staging lane could in principle publish production.

My recommendation: put the staging item under a separate publisher account. The alternative is to skip the store for staging and test the unpacked build only.

Questions I'd want answered in week one

  1. Do the matching rules live inside the extension, or does the backend send them per portal?I default to inside: they are reviewed, hashed and signed with each release, and the backend can only send values. Backend-supplied rules need their own signing path (+10 hours).
  2. Is a ticket held in the worker's memory acceptable under "stores nothing"?It is an opaque token, never a value, and it disappears when Chrome stops the worker. The alternative, chrome.storage.session, survives worker restarts but is a storage API, so I won't use it without your sign-off.
  3. Can the staging item live under a separate Web Store publisher?Service-account access is publisher-wide, so separation is the only way to keep a staging token from being able to publish production.
  4. Who signs release tags, and who approves the release environment?Ideally two different people, so no single account can ship a release alone.
  5. Do any target portals put the form inside an embedded frame from another site?If so, frame support is a defined addition (+8 hours), and the report already counts frames so we will see it early.
